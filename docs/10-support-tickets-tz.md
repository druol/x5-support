# 10. Тестовое задание — «Сервис заявок поддержки»

> Полный текст ТЗ (на случай, если у AI-агента нет доступа к PDF).
> Ориентир: 6–8 часов. Технологии свободные. AI-инструменты разрешены.

## 1. Интерфейс пользователя

- Создание заявки: **тема** («Проблема с доступом» / «Ошибка в работе сервиса» / «Другое»),
  **заголовок**, **описание**. Все поля обязательны.
- Пользователь видит **список своих заявок** и открывает каждую: статус, история изменений,
  комментарии, добавление комментария.
- Регистрации/авторизации нет: два отдельных раздела — **пользователь** и **администратор**
  (в системе один пользователь и один администратор).

## 2. Интерфейс администратора

- Видит все заявки: **номер, тема, заголовок, статус, дата создания**.
- Фильтрация по **теме** и **статусу**.
- В карточке заявки: комментарии и смена статуса.

## 3. Жизненный цикл заявки

| Действие | Результат |
|---|---|
| Пользователь создаёт заявку | статус **«Новое»** |
| Администратор принимает заявку | статус **«В работе»** |
| Администратор завершает заявку | статус **«Выполнено»**, комментарий с результатом **обязателен** |
| Пользователь выбирает «Вернуть в работу» | статус снова **«В работе»**, комментарий с причиной **обязателен** |

- «Вернуть в работу» доступно **только для выполненной** заявки.
- Для каждого комментария и изменения статуса видны **автор и время**.

## 4. Уведомления

- В интерфейсе пользователя — **колокольчик со счётчиком непрочитанных**.
- Уведомление появляется, когда администратор: принимает заявку в работу, добавляет
  комментарий, завершает заявку (для завершения достаточно одного уведомления с результатом).
- Клик по колокольчику — список уведомлений, **начиная с новых**; в уведомлении: номер заявки,
  описание события, время. Клик открывает заявку и отмечает уведомление прочитанным.
- Новые уведомления появляются **без ручной перезагрузки страницы** (способ обновления — на выбор).
- **Уведомления — отдельный сервис.** Работа с заявками **не должна ждать** создания уведомления.
  Если сервис уведомлений недоступен, администратор продолжает работу; после восстановления
  пропущенные уведомления появляются автоматически.
- Повторная обработка одного события **не создаёт дубликаты**.
- Уведомления и признак прочтения **сохраняются после перезапуска**.

## 5. Границы задания

- Технологии, БД и способ взаимодействия сервисов — на выбор.
- Данные заявок сохраняются после перезапуска.
- Достаточно простого функционального интерфейса; авторизация, вложения, почта и сложный
  дизайн не требуются.
- Если не успеваете — предоставить рабочую часть и описать ограничения.

## 6. Что предоставить

1. Репозиторий с исходным кодом.
2. Инструкцию запуска всех компонентов.
3. Краткое описание архитектуры и принятых решений.
4. Инструкцию проверки основного сценария и восстановления уведомлений после сбоя.

На обсуждении нужно объяснить код, решения и способ проверки.

## 7. Критерии приёмки

- ✅ Полный цикл: создать → принять в работу → прокомментировать → завершить → вернуть в работу с причиной.
- ✅ Уведомления появляются в колокольчике, открывают нужную заявку и отмечаются прочитанными.
- ✅ При недоступности сервиса уведомлений работа с заявками продолжается.
- ✅ После восстановления сервиса уведомления доставляются без потерь и дубликатов.
